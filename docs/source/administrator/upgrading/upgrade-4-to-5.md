# Major upgrade: 4.\* to 5.\*

zero-to-jupyterhub 5.0 is a major upgrade that may require some changes to your configuration,
depending on what features you may use.
This mostly comes in the form of some upgraded packages, described below.

:::{seealso}

- the [general upgrade documentation](upgrading-major-upgrades) for upgrade steps to take every time you do a major chart update
- the [changelog](changelog-5.0) for details of upgraded packages

:::

## JupyterHub 6

zero-to-jupyterhub 6.0 upgrades the JupyterHub version from 5.5.5 to 6.2.0.
As major upgrades go, this is not a big one.
It does include a tiny database schema upgrade, so make sure to backup your database before upgrading.
If you use sqlite (the default), JupyterHub does this automatically.

:::{seealso}

For more detailed changes in JupyterHub, see JupyterHub's own documentation on upgrading to version 6:

Especially if you use features like:

- named servers
- passing spawn options via URL or API

- [JupyterHub changelog](https://jupyterhub.readthedocs.io/en/6.2.0/reference/changelog.html)
- [Upgrading to JupyterHub 6](https://jupyterhub.readthedocs.io/en/6.2.0/howto/upgrading-v6.html)

:::

### Named server restrictions

If you are using named servers, JupyterHub 6 introduces new restrictions on their names,
which may affect your use cases, if your server names happen to fall outside the new rules.

:::{seealso}

- [Named Server Restrictions](https://jupyterhub.readthedocs.io/en/6.2.0/howto/upgrading-v6.html#named-server-restrictions)
  :::

### aiohttp

JupyterHub 6 switches internal HTTP requests to use aiohttp instead of tornado (pycurl).
Hopefully, this should _improve_ the behavior of JupyterHub's internal requests under load.

But if you encounter issues, please report them.

One issue that's been reported so far is DNS caching.
If you encounter issues with JupyterHub pods not responding after restart,
it may be that the DNS cache is stale.

Adding this snippet to your Python configuration avoids the (currently) not configurable c-ares cache used by aiodns:

```python
import aiohttp.connector
from aiohttp.resolver import ThreadedResolver
aiohttp.connector.DefaultResolver = ThreadedResolver
```

:::{seealso}

- [issue report for aiodns cache](https://github.com/jupyterhub/jupyterhub/issues/5556)

:::

## Existing secrets

If you choose to specify values config using `jupyterhub.existingSecret`,
the chart will no longer generate any random secret values by default.
The existing secret **MUST** now contain at least the following fields:

| field                                       | description                     |
| ------------------------------------------- | ------------------------------- |
| hub.config.ConfigurableHTTPProxy.auth_token | (random string)                 |
| hub.config.JupyterHub.cookie_secret         | (hex string, 64 chars)          |
| hub.config.CryptKeeper.keys                 | (hex string, 64 chars)          |
| hub.services.<name>.apiToken                | (one entry per service, if any) |

which are generated by default when `existingSecret` is not defined.
These secrets were previously generated unconditionally.
